# Install the integration image

## Minimal test deployment

```yaml
services:
  dockman:
    image: ghcr.io/cerede2000/dockman:integration
    container_name: dockman
    environment:
      DOCKMAN_COMPOSE_ROOT: /server/stacks
      DOCKMAN_CONFIG: /config
    volumes:
      - /server/stacks:/server/stacks
      - /server/appdata/dockman:/config
      - /var/run/docker.sock:/var/run/docker.sock
    ports:
      - "8866:8866"
    restart: unless-stopped
```

Open `http://HOST:8866`.

:::warning
Mounting `/var/run/docker.sock` gives Dockman Docker-daemon authority. A socket proxy is recommended for a persistent installation.
:::

## Path requirement

The stack path must be the same absolute path in all three places:

1. `DOCKMAN_COMPOSE_ROOT=/server/stacks`;
2. host mount source `/server/stacks`;
3. container mount target `/server/stacks`.

This is required because Compose bind paths must remain meaningful to the Docker host. The mount must be writable for the editor, Git imports and provisioning. Use `rslave` propagation with the autonomous Secrets runtime: host-created tmpfs mounts enter Dockman, while container-created mounts cannot propagate back to the host.

## Hardened socket-proxy deployment

The following example shows the important Dockman-side settings. Complete the proxy permissions with the [socket-proxy guide](../docker-socket/index.md).

```yaml
services:
  dockman:
    image: ghcr.io/cerede2000/dockman:integration
    container_name: dockman
    depends_on:
      socketproxy:
        condition: service_healthy
    environment:
      DOCKER_HOST: tcp://socketproxy:2375
      DOCKMAN_COMPOSE_ROOT: /server/stacks
      DOCKMAN_CONFIG: /config
      DOCKMAN_AUTH_ENABLE: "true"
      DOCKMAN_AUTH_USERNAME: admin
      DOCKMAN_AUTH_PASSWORD: ${DOCKMAN_AUTH_PASSWORD:?required}
      DOCKMAN_GIT_SYNC: "true"
      DOCKMAN_GIT_MASTER_KEY_FILE: /run/secrets/dockman_git_key
      DOCKMAN_NOTIFICATION_MASTER_KEY_FILE: /run/secrets/dockman_notification_key
      DOCKMAN_GIT_STORAGE_PATH: /git-data
      TZ: Europe/Paris
      PUID: "0"
      PGID: "0"
    secrets:
      - dockman_git_key
      - dockman_notification_key
    volumes:
      - /server/stacks:/server/stacks:rslave
      - /server/appdata/dockman/config:/config
      - /server/appdata/dockman/git:/git-data
    read_only: true
    tmpfs:
      - /tmp:rw,noexec,nosuid,size=128m,mode=1777
    cap_drop:
      - ALL
    cap_add:
      - CHOWN
      - DAC_OVERRIDE
    security_opt:
      - no-new-privileges:true
    ports:
      - "8866:8866"
    healthcheck:
      test: ["CMD", "wget", "--quiet", "--spider", "http://127.0.0.1:8866/"]
      interval: 30s
      timeout: 5s
      retries: 3
    restart: unless-stopped

secrets:
  dockman_git_key:
    file: ./secrets/dockman_git_key
  dockman_notification_key:
    file: ./secrets/dockman_notification_key
```

Generate each master key as 32 random bytes or base64-encoded 32-byte material and store it outside the Dockman config volume. Losing a key makes the corresponding stored credentials unreadable.

### Read-only root filesystem and PUID/PGID

The entrypoint creates users and groups when `PUID` is non-zero. That requires a writable `/etc`. With `read_only: true`, run with `PUID=0` and `PGID=0`, then use `cap_drop`/`cap_add` as shown. `CHOWN` is needed only when provisioning deliberately changes ownership; `DAC_OVERRIDE` is needed to manage stack files that root may access but normal mode checks would reject.

If you do not need cross-owner provisioning, omit `CHOWN`. Always test create, chmod and chown operations against the actual stack filesystem before enabling automatic provisioning.

## Persistent data

Back up these locations together:

| Path | Purpose |
|---|---|
| `/config` | SQLite database, settings, Docker CLI state, generated keys when explicit secrets are not used |
| `DOCKMAN_COMPOSE_ROOT` | Compose and configuration files managed by Dockman |
| `DOCKMAN_GIT_STORAGE_PATH` | Compact Git objects and Git synchronization backups when configured separately |
| master-key secrets | Required to decrypt Git and notification credentials |

Do not place `/config` or `/git-data` inside the managed stack tree.

## Updating Dockman

The Settings page provides separate **Check for update** and **Update** actions. The update action remains available even when the digest is current so a Compose/configuration change can recreate Dockman.

For rollback safety, pin the image digest used for a validated deployment. The moving `integration` tag is intended for testing current development work.

## Custom SMTP CA

For a private SMTP relay using STARTTLS:

```yaml
environment:
  DOCKMAN_SMTP_CA_FILE: /etc/ssl/certs/smtp-ca.crt
volumes:
  - /server/certs/smtp-ca.crt:/etc/ssl/certs/smtp-ca.crt:ro
```

The file must contain the issuing CA chain in PEM format, not merely an unrelated server certificate. TLS verification is never disabled.
